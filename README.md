Stillum CMS — Корпоративная медиа-платформа и система дистрибуции контента

Краткое описание кейса:

Проектирование и сопровождение разработки специализированной B2B/B2C медиа-платформы для независимого музыкального лейбла. Система решает проблему удержания аудитории и дистрибуции тяжелого контента, объединяя бесшовный Lossless-аудиостриминг и механики прямого социального взаимодействия «Артист — Слушатель».

📌 1. Бизнес-контекст и проблематика (AS-IS)

Проблема заказчика:

Музыкальный лейбл (продюсерский центр) столкнулся с двумя критическими ограничениями:

Зависимость от стриминговых агрегаторов (Яндекс.Музыка, VK Музыка, Spotify):

Потеря прямого контакта с аудиторией (агрегаторы монополизируют пользовательские данные).

Высокие комиссии платформ и невозможность выстроить прямую платную подписку на эксклюзивы.

Неприменимость стандартных CMS (WordPress, 1С-Битрикс):

Многостраничная архитектура (MPA) приводит к полной перезагрузке страниц при навигации: воспроизведение аудио прерывается.

Отсутствие реактивного социального модуля: обсуждения релизов уходят во внешние соцсети, что снижает показатель Session Retention Rate.

Цель проекта (TO-BE):

Спроектировать архитектуру и бизнес-логику независимой Web-платформы, позволяющей:

Обеспечить непрерывный (бесшовный) стриминг аудиопотока при свободной навигации по каталогу.

Замкнуть коммуникацию вокруг релизов внутри собственного портала (реакции, ветки комментариев, верифицированные ответы артистов).

Сократить совокупную стоимость владения (TCO) платформой в сравнении с кастомизацией тяжелых коробочных CMS.

🔄 3. Моделирование бизнес-процессов

Сравнительный анализ процессов публикации и потребления:

AS-IS: Артист передает файл $\to$ Администратор публикует в статический архив $\to$ Слушатель включает трек $\to$ Для обсуждения уходит во внешние соцсети $\to$ Разрыв контекста и отток трафика.

TO-BE: Артист публикует релиз через личный кабинет $\to$ Файл напрямую отгружается в S3, метаданные валидируются в СУБД $\to$ Слушатель потребляет стрим без пауз при навигации $\to$ Обсуждение ведется в боковой панели $\to$ Артист модерирует комментарии $\to$ Трафик удерживается внутри платформы.

🔐 4. Ролевая модель доступа (RBAC)

На основе матрицы доступа разработана Use Case диаграмма (UML) со строгим разграничением привилегий:

[ Слушатель (FREE) ]
  ├── Авторизация сессии (JWT)
  ├── Воспроизведение аудиопотока (MP3)
  ├── Формирование пользовательских плейлистов
  └── Публикация комментариев и базовых реакций

[ Премиум-клиент (PLUS) ] ── (наследует права FREE)
  ├── Доступ к Lossless-аудиопотоку (WAV/FLAC)
  └── Кастомизация интерфейса (персональные фоны, бейджи)

[ Артист (ARTIST) ] ── (наследует права PLUS)
  ├── Публикация и модерация аудиорелиза
  ├── Управление метаданными треков
  ├── Модерация комментариев: верифицированная отметка «Понравилось автору»
  └── Доступ к приватной аналитике прослушиваний


🗄️ 5. Проектирование базы данных и архитектура хранения

Нормализация и структура (PostgreSQL):

Схема базы данных декомпозирована до 3-й нормальной формы (3NF) для предотвращения аномалий обновления и дублирования:

User — системные сущности пользователей и ролевые атрибуты (RBAC).

Track — метаданные аудиозаписей (связь 1:N с артистом).

Comment & Reaction — дерево обсуждений с каскадным удалением (ON DELETE CASCADE).

TrackLike / PlaylistLike / Follows — реализация социальных связей M:M через промежуточные таблицы с составными первичными ключами (Composite PK: userId + trackId), оптимизированными B-Tree индексами.

Notification — журнал событий. Поле payload спроектировано с использованием типа данных JSONB для полиморфного хранения контекста уведомлений без нарушения реляционной строгости.

Безопасность и адресация:

Все сущности используют UUID v4 вместо последовательных целочисленных идентификаторов (Serial ID), что исключает возможность перебора ссылок (ID Enumeration Attacks) и парсинга закрытого контента.

Декомпозиция хранения (Hybrid Storage Pattern):

Реляционная СУБД (PostgreSQL): хранит исключительно структурированные текстовые данные, связи и метаданные.

Облачное хранилище (S3-compatible Object Storage): принимает тяжеловесные бинарные медиафайлы (WAV/MP3). Стриминг и прямая загрузка осуществляются по временным безопасным URL (Presigned URLs), полностью разгружая центральный сервер приложений.

⚡ 6. Интеграционная архитектура и NFR (Нефункциональные требования)

Отказ от классического REST API:

В качестве протокола клиент-серверного взаимодействия обоснован выбор Server Actions (RPC-модель Next.js):

Проблема REST: Необходимость проектирования десятков CRUD-эндпоинтов, сериализации JSON и дублирования валидационных схем на клиенте и сервере.

Решение: Прямой вызов типизированных серверных функций из UI-компонентов. Исключен лишний сетевой слой, обеспечена сквозная статическая типизация (End-to-End Type Safety) и минимизирован объем инфраструктурного boilerplate-кода.

Управление состоянием и паттерн Optimistic UI:

Бесшовный стриминг: Состояние аудиоплеера изолировано в глобальном сторе Zustand вне дерева страниц (SPA-подход). Переходы по маршрутам не триггерят размонтирование аудиопотока.

Снижение субъективной задержки до 0 мс: Реактивные пользовательские действия (лайк, добавление комментария) обновляют UI мгновенно. Транзакция отправляется на сервер в фоновом режиме; при возникновении сбоя сети срабатывает автоматический Rollback к исходному состоянию с выводом уведомления пользователю.
